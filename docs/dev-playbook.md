# 通用开发实践手册

> **定位**：这份文档与具体项目无关，沉淀的是「在有门禁、有 CI、由人（或人 + AI 代理）协作推进的仓库里，怎么把改动安全地送进主干」。
>
> **来源**：DanmuFloat 项目 36 轮自迭代过程中的真实教训，每条规则都对应附录 B 里一次实际事故，没有凭空总结的「最佳实践」。
>
> **三层结构**：母原则（为什么）→ 机械动作（怎么做，可直接照抄）→ 附录 A 本仓库绑定 / 附录 B 事故档案（证据）。
>
> **怎么用**：动手前读 §1~§3；写代码时对照 §5~§7；提 PR 前逐条过 §10 清单；踩了新坑就补进附录 B 并给编号——**没有编号的教训等于没沉淀**。

---

## 0. 三条母原则

1. **验证能力决定范围，而不是反过来。**
   先问「这个改动我能验证到什么程度」，再决定做不做、做多大。验证不了的东西，收益再大也只会变成一次盲改：它可能碰巧是对的，但你没有任何证据，下一个改动就会把它推翻。推论：**当一个环境只能验证纯逻辑时，就不该在该环境里做原生 / 依赖 / 通道类改动**——正确结论是「不做」或「降级为文档 + 手工步骤」，不是「先做了再说」。
2. **单一目的、小步、可回滚。**
   不是审美要求，而是**失败定位成本**：反馈越慢、越粗糙（例如只有一条远程 CI 流水线），一次失败能指出的范围就越小。PR 越大，一次红就等于一次盲猜。
3. **事实以当前状态为准，不以记忆和叙述为准。**
   分支在哪、`origin/main` 在哪、CI 是第几次运行、文件现在长什么样——**动手前重新读一遍**。这份文档里超过一半的事故，根因都是「我记得它应该是那样」。

## 1. 开工前：基线与分支纪律

**规则：每次开工、以及每次提 PR 之前，都先同步远端，并从最新的 `origin/main` 拉分支。**

为什么这一条要放在最前面：分支基线不是 `origin/main` 时，**PR 会静默地混入不属于本次改动的提交**。这类 PR 的 diff 看起来「多几个文件」，但 review 时极易被当成正常改动放过去，合入后就把别人未完成的工作带进了主干。

```bash
# 1) 同步并确认基线
git fetch origin
git checkout main && git pull --ff-only
git log --oneline -1 origin/main          # 记下这个 commit，它就是你的基线

# 2) 从远端 main 拉分支（不要从当前 HEAD 拉）
git checkout -b <类型>/<简短描述> origin/main
git branch --show-current                 # 确认自己在目标分支上

# 3) 提 PR 前再 pull 一次（第 1 步可能已是几小时前）
git fetch origin && git checkout main && git pull --ff-only
```

**两条硬核对，缺一不可：**

- `git log --oneline -1 origin/main` 必须是你分支的祖先（`git merge-base --is-ancestor origin/main HEAD`）。
- `git show --stat` 的文件数必须等于你本次真正打算改的文件数。**多出来的文件就是别人的工作**，此时不要继续，回到第 1 步重做。

**顺带一条容易忽略的**：不要假设「最新的 PR 号是我上次看到的那个」。仓库可能在你离开期间前进了很多；开工先看一眼 `gh pr list` 和 `git log origin/main`，比事后发现自己建在过期基线上便宜得多。

## 2. 门禁纪律：CI 是唯一事实

- **不绿不合并。** 如果仓库把警告也算失败（`No issues found` 这类），那么**警告等同于失败**，没有「只是 warning 可以放过」。
- **不要用「上次的结果」判断当前状态。** 典型陷阱：向一个**已关闭**的 PR 分支 push 不会触发新的 CI，此时 `gh pr checks` 返回的是**上一次运行的陈旧结论**。要么 `reopen` 该 PR，要么新开一个，再判断。
- **读日志要一次读全。** 至少覆盖：失败步骤名、`error`、`warning`。只 grep `error` 会让你漏掉「警告即失败」这类门禁，白推一轮。
- **从耗时判断失败类型**：静态检查 / 编译通常在 1 分钟内失败，测试要更久。这条经验能让你在拉日志之前就缩小范围。
- **合入后确认主干状态**：合并是「PR 绿」+「主干更新」两件事，都要核对，而不是合上就完事。

---

## 3. 变更粒度：单一目的

- 一个 PR 只做一件事；重构与功能分开、文档与代码分开、格式化与逻辑分开。
- 判断标准很机械：**如果这次失败，你能一句话说出大概是哪一处的问题吗？** 说不出来就是太大了。
- 禁止顺手改无关代码。想改的东西记下来，作为独立 PR 或写进台账——「顺手」是 review 成本与回归风险的主要来源。
- 用不到的中间状态宁可分 PR，也不要塞进同一个 PR 的多个 commit 里：评审看的是 PR 的整体 diff。

## 4. 编辑纪律：长文件、锚点与批量替换

改长文件最容易出事，因为「字符串替换」在文本层面永远成功，在结构层面可能已经错了。

**规则：按块切片替换，而不是全局字符串替换。**

1. **锚点必须先断言唯一。** 替换前统计出现次数，必须恰好为 1；否则停下来换更长的锚点。
   `if (anchor.split(needle).length - 1 !== 1) throw` —— 这类断言应该写进你的替换脚本，而不是靠眼睛。
2. **锚点撞车是常态，不是意外。** 同一行代码往往在多个类、多个构造函数、多套预设里重复出现。正确做法是先按结构切片（`class X {` … 第一个 `}`；函数签名 … 匹配的 `);`），**只在切片内**替换。
3. **多行锚点回填时，不要把锚点首行再写一遍。** 这是最隐蔽的一类结构破坏：文件语法仍然「看起来对」，但多了一层嵌套（列表里多了一个 `key: [`）。
4. **幂等守卫要按「块」判断，不能按「整个文件」判断。** 用「文件里是否已出现过某字符串」来跳过已完成的插入，会让**其他块**的插入被整段跳过——而错误通常要等到编译期才暴露（缺必填参数）。
5. **改完立刻回读该区域，并跑一次括号/括号配对检查**，不要等 CI。CI 是最后一道网，不是第一道。
6. **改「必填参数 / 抽象成员」前，先列出所有构造点与实现点**（grep 类名 + 调用形态）。漏掉任意一个都会直接编译失败；这类错误完全可以避免。
7. **测试代码同样适用**：生成出来的测试要先回读一遍，尤其是"把它们拼出来"的模板代码。

## 5. 语言细节陷阱（以 Dart 为例，思路可迁移）

这些不是风格问题，而是**编译期就会炸**的硬约束：

- **`const` 上下文里不能调用方法。** `Colors.white.withValues(alpha: 0.94)` 放进 `const` 构造函数会直接报 `const_eval_method_invocation`。替代方案是等值字面量（`0.94 × 255 = 240 = 0xF0` → `Color(0xF0FFFFFF)`），并且**等值性可以用 `toARGB32()` 断言**，不必牺牲测试精度。
- **字符串插值 `$0xFF...` 非法。** `'key_$0xFF00BCD4'` 里的 `$0` 会被解析成标识符（`Expected an identifier`），要写 `${0xFF00BCD4}`；同时插值表达式不构成常量，含插值的 key 不能标 `const`。
- **「相等」写法有漂移风险。** 颜色、浮点、序列化结果优先比较规范化后的整数/字节（如 `toARGB32()`），而不是比较对象或带 alpha 的浮点表示。
- **对齐上游代码时不要顺手改成自己的 lint 风格**（内联的第三方源码尤其如此）：那会让 diff 无法 review，也会让下次同步上游变成冲突。

## 6. 测试纪律：断言要证明实质，不是复述现状

- **写测试前先读被测代码。** 契约不能靠猜：曾有一个解析函数要求 `type` 字段与 `opacity` 同时存在，而测试只给了其中一个，于是三条用例全红、还以为是实现有问题。**失败时先怀疑测试的前提，再怀疑实现。**
- **「等于某个参考值」往往什么都没证明。** 更强的断言是「**输入变了，输出必须跟着变**」。例如要证明某函数没有退回「按开关猜」的实现，就改掉数据源里的一个字段，断言输出随之改变——「等于 A」和「不等于 B」两者都证明不了这件事。
- **写「设计守卫」型断言。** 数量/映射一一对应、枚举覆盖、每个角色都有展示名……这类不变量测试能在实现漏一半时立刻报警，而普通用例不会。它的价值在于：**它拦住的是"看着合了、实际不可用"的交付**。
- **UI 测试的精确语义**：`find.byType` 是运行时**精确**类型匹配；`find.text` 是精确匹配且忽略 offstage 节点；目标在视口外时 `tap` 会**静默失败**，先 `ensureVisible`。
- **`Bad state: No element` + 堆栈含 `getCenter`** 意味着 finder 命中了 0 个元素，与回调逻辑无关。
- **被测行为是「值」时，直接驱动回调**（`widget.onChanged!(...)`）比猜命中区域更诚实；命中区域本身要测的话，就单独写一条针对命中区的用例。
- **不要为了凑测试而给生产代码加注入口。** 那是独立的前置改动：要么单独一个 PR，要么**把测试范围诚实收窄并写明原因**（哪些断言覆盖了、哪些留到后续）。为了测试方便而扩大生产代码的表面积，是拿可维护性换覆盖率。
- **测试文件与环境限制要写在用例里**（例如「每个测试文件只能 mount 一次」），否则后来者会踩同一个坑。

## 7. 协作纪律：人 + 只读代理

当执行者与决策者分离（人或 AI 代理）时：

- **写者唯一。** 同一时间只有一个执行者改文件；只读角色只产出裁决、审查、文档。
- **审批与范围问题交给只读的决策角色**，执行者不自行放宽范围——尤其是「顺手把它也做了」这种。
- **裁决必须落文档。** 口头/会话内的结论会随上下文丢失，下一轮会被重新讨论，或被执行成另一个版本。
- **执行者不得引入新的宿主机环境要求**（装工具链、改系统配置）；也不应新增依赖 / 权限 / 后台机制 / 原生通道，除非能论证它不改环境且收益足够。**先冒烟、再动工**：无法在本环境冒烟的方案，直接判「不做」或「降级为文档 + 手工步骤」。
- **规范要能被外行机械执行。** 写「注意分支」没用，写「提交前第一件事是 `git branch --show-current`，不是目标分支就先 checkout」才有用。

## 8. 文档与台账纪律：前后必须一致

追加式台账（每轮往文件尾部追加）必然会前后脱节，**必须有人回头对齐顶部摘要**。

- **顶部摘要 = 当前事实；尾部记录 = 历史过程。** 两者冲突时以「更靠后的收口 / 交付记录」为准，并把这条优先级写进文档开头，否则每个读者都要自己猜。
- **结论被推翻时，回到原处加注**（「已推翻 / 已更正 → 指向新结论」），而不是只在新章节写新结论。否则同一个文件里会同时存在两个互相矛盾的结论。
- **废弃措辞要清零**：「待裁决」「未开始」「待做」「⬜」这类词，在裁决与交付之后必须改。文档里最危险的不是错误，是**过期**——它看起来仍然可信。
- **数字与引用写进去之前复算一次**（比例、行号、commit、PR 号）；写错了要在原处更正，而不是在别处补一句。
- **文档地图要显式声明**：哪份文档管什么、谁覆盖谁。读者不该靠翻三个文件来猜哪个是权威。

## 9. 交付前检查清单（每次提 PR 前逐条过）

- [ ] 已同步：`git fetch origin && git checkout main && git pull --ff-only`
- [ ] 分支从 `origin/main` 拉出，且 `origin/main` 是它的祖先
- [ ] `git show --stat` 的文件数 == 本次实际改动的文件数（**没有别人的工作**）
- [ ] `git branch --show-current` 是目标分支（不是 `main`，也不是别人的分支）
- [ ] 单一目的：没有无关重构、格式化、文档混入
- [ ] 新增 / 修改的行为都有测试；测试断言的是**实质**而非现状
- [ ] 长文件替换已按块切片 + 唯一性断言 + 改后回读
- [ ] 门禁命令与本仓库 CI 完全一致；本地跑不了时，明确知道 CI 会跑什么
- [ ] 提交信息符合本仓库规范（类型 / 范围 / 描述）
- [ ] 台账与文档已同步（含「已推翻」的原处更正）
- [ ] 若踩了新坑：已补进附录 B 并编号
